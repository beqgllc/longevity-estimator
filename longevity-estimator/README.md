# Longevity Estimator

A privacy-conscious web application concept for collecting self-reported demographic, geographic, medical, occupational, behavioral, and lifestyle information and presenting **population mortality estimates** or, only when supported by a compatible validated model, **individualized survival estimates**.

> **Important limitation:** no questionnaire can determine the exact date, hour, minute, or second of an individual's death. Any months/days/hours/minutes/seconds shown by this application are arithmetic conversions of a statistical expected value, not precision predictions. This application is not a diagnostic tool and does not replace advice from a qualified healthcare professional.

## Project status

This repository documentation describes the intended architecture and governance. Do not assume that a validated individualized mortality model or licensed mortality dataset is already installed simply because an interface exists. The application must expose its actual implementation and data status in the UI.

The project supports two clearly separated output states:

1. **Baseline actuarial estimate:** a result calculated from a relevant, documented life table. It is a population-based estimate and must be labelled as not individually adjusted.
2. **Validated individualized estimate:** a result generated by a survival model whose population, input requirements, assumptions, calibration, validation, and forecast horizon are documented and applicable to the person being assessed.

If neither state can produce a defensible result, the app must explain why and must not invent a number.

## Core principles

- Scientific validity before numerical polish: never invent model coefficients, risk multipliers, “years lost,” confidence intervals, or disease-specific adjustments.
- Transparent provenance: record the source, version, population, period, licensing, and processing steps for every dataset and model.
- Missing is not no: unknown, declined, and not-applicable answers remain distinct.
- Privacy by default: no account or persistent storage should be required for the basic anonymous workflow.
- Least privilege: avoid collecting more personally identifiable or sensitive information than the calculation needs.
- Inclusive handling: demographic identity is not itself a diagnosis or a justification for an arbitrary mortality penalty.
- Replaceable models: questionnaire and UI code must not contain statistical coefficients or calculation logic.
- Honest uncertainty: predictions must be limited to the supported population and time horizon.

## Intended stack

The reference architecture assumes Next.js App Router, React, TypeScript, Node.js, schema validation, unit/integration tests, and GitHub Actions. Adapt to an existing working stack instead of migrating solely to match the suggested structure.

Use an actively supported Node.js LTS release. Next.js documents Node.js 20.9 as its current minimum; this project’s CI template uses Node.js 24 LTS as a deployment/runtime target, subject to compatibility checks at implementation time. ## Getting started

Prerequisites:

- Node.js LTS compatible with the checked-in framework version.
- npm and a committed `package-lock.json` if using npm.
- Git.

Once the application code and `package.json` exist:

```bash
npm ci
npm run dev
```

Then open the local URL shown by the development server (Next.js normally uses `http://localhost:3000`). For a production build:

```bash
npm run lint --if-present
npm run typecheck --if-present
npm run test:ci --if-present
npm run build
```

The included CI workflow expects `npm ci` and `npm run build` to be available. Add the optional scripts above to `package.json` as those capabilities are implemented. Do not claim tests passed until they have been executed against the repository.

## Estimation modes

### Baseline-only mode

- Select the most appropriate available life table.
- Record table year, population definition, and stratification variables.
- Calculate the baseline estimate using the table’s documented definitions.
- State which geographic/demographic details were and were not used.
- Do not claim that questionnaire answers altered mortality if no validated adjustment model ran.

### Individualized mode

- Confirm model applicability before calculation.
- Require all model-required features or follow the model’s documented missing-data method.
- Use model-compatible baseline assumptions and the model’s own transformations.
- Report model identity, version, population, forecast horizon, and available validation metrics.
- Refuse unsupported extrapolation or clearly label restricted mean survival time when only a finite horizon is supported.

## Statistical outputs

Where supported, results may include:

- Expected remaining lifespan, calculated from the area under a survival curve.
- Median remaining survival time, only if the survival curve crosses 0.5 within the supported horizon.
- Survival probabilities at validated horizons such as 1, 5, 10, or 20 years.
- A statistically defensible uncertainty interval, only if the model provides a valid method to calculate one.
- A summary of model features used, missing values, source data, and limitations.

Do not call a finite-horizon restricted mean survival time “full remaining life expectancy.” Do not produce an exact predicted death date or ticking countdown.

## Security and privacy

Never commit real secrets, raw questionnaire answers, identifiable assessment exports, private clinical records, or unlicensed restricted datasets. Use `.env.example` for non-secret configuration names only. A `.gitignore` should exclude `.env*` files except `.env.example`, local databases, exports, logs, build output, and personal data.

Read [`docs/privacy-and-security.md`](docs/privacy-and-security.md) before enabling persistence, analytics, external APIs, user accounts, or production use.

This repository is an engineering and statistical framework. It is not, by itself, clinical validation or proof of regulatory compliance. Obtain appropriate professional review before production deployment.
